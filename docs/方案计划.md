## 一、结论先行（可行性判定）

**技术上可行，但这不等于「把仁王2的 MOD 搬过去」。它是一次中等规模的引擎级逆向工程。**

三句话概括：

1. **好消息**：仁王 1 与仁王 2 属同一引擎家族（KTGL / `ktgl` 命名空间，`Character::AddStateObject*` 状态架构），
   而且仁王 1 的 `nioh.exe` **静态数据段没有加密**——里面保留了 2521 个 RTTI 类型名和近 2 万条引擎字符串，
   其中直接就有 `Refer::IsAttackGuard`、`Player::RecoverStamina`、`AddStateObjectStaminaDamageRate` 等
   与精防强相关的符号。锚点是"找得到"的。
2. **坏消息**：`nioh.exe` 的**代码段 `.text` 在磁盘上是加密的**（Steam DRM / SteamStub）。
   熵值 8.000、256 个字节值均匀分布、`E8 rel32` 调用目标只有 0.41% 落在段内、
   `48 89 5C 24` 这类 MSVC 常见序言出现 0 次 —— 这些指标说明磁盘上根本没有可读代码。
   **所以任何 AOB 签名都必须从"运行中的进程内存"里取。**
3. **现实约束**：仁王 2 那个精防 MOD 的**源码不在本机**（我已扫描全部 48 个 DSH 历史会话，
   只有当前会话提到它）。它只有 DLL，且锚点是为 `nioh2.exe` 定制的，不能直接复用。
   我们能把它当**行为规格书 + 架构范本**，但仁王 1 的锚点必须重新找。

## 二、已完成调研：事实与证据

### 2.1 两个压缩包是什么

### 2.2 加载器（pkg1）——**可复用到仁王 1**

反汇编/字符串证据：

- 内部名 `NiohNativeModLoader`，PDB 路径 `C:\Users\balfa\source\repos\NiohNativeModLoader\dinput8\x64\Release\dinput8.pdb`。
- 是 **x64** `dinput8.dll` 代理：转发 `DirectInput8Create` 到系统 dinput8，然后在后台线程里
  扫描游戏目录下的 `mods\` 文件夹，对每个 `.dll` 调 `LoadLibraryW`。
- 字符串：`[Loader] Scanning mods directory`、`[Loader] Loading mod: `、`Global\NiohModLoader_Init`、
  日志文件 `loader.log`、覆盖窗口 `NiohModLoaderOverlay`（`Mod Loader active`）。
- **关键：它不校验 exe 名字**（没有任何 `nioh2.exe` / `Nioh3.exe` 之类的字符串），纯粹按目录加载。
- **仁王 1 可用的前提已满足**：`nioh.exe` 的导入表里有 `DINPUT8.dll → DirectInput8Create`，
  代理链成立。（pkg1 的 README 里写 `Nioh3.exe` 只是文案，与二进制行为无关。）

> ⚠️ 一个待验证点：加载器是否递归扫描 `mods\` 子目录（README 的目录示例是带子目录的）。
> 阶段 0 会用最小探针实测。

### 2.3 仁王 2 精防 MOD（pkg2）——架构范本

从 DLL 的导出表、导入表和 `.rdata` 字符串表还原出的设计：

**导出 API**（说明它内部分层，且有可外部驱动的接口）：
`PG_Initialize`、`PG_InputUpdate`、`PG_KiSubtract`、`PG_RecoveryCheck/Start/Stop/Dump/Report/GetCancel/SetCancel`、
`PG_CapUpdate`、`PG_SetMode/GetMode`、`PG_ConfigureWindow/Reward/Recovery/EnemyKi/EnemyEffects/Anima`、
`PG_DumpLog`、`PG_GetVersion`。

**核心机制 = AOB 签名扫描 + 多重校验**（这是最重要的架构结论）：

- `AOB: %s; no hooks installed`、`AOB: verified unique anchors and instruction-derived targets`
- `AOB: %s %s (matches=%u); no hooks installed`、状态枚举 `unreadable/scan timeout`、`ambiguous`、`not found`
- 锚点名称：`guard input`、`Ki/Cap settlement`、`recovery dispatch`、`player slot accessor`、
  `controller vtable reference`、`enemy HP reflection path`、`impact submit`、`cap consume`、
  `cap condition call`、`cap condition ABI`、`input_call`、`ki_call`、`cap_call`、`input_edge`、`recovery_context`
- 校验强度很高：会验证 matches 数量唯一、验证 CALL 目标/ABI、验证写入目标是否落在可写镜像数据、
  验证 vtable 是否只读、验证原始 CALL 字节可读。失败则整组不安装（`no hooks installed`），不会半死状态。
- **不依赖 exe 哈希**：`AOB: player_slot=0x... controller_vtable=0x...; instruction-derived addresses; no EXE hash/profile lookup`。
  （它只是把 exe 的 sha256 打进日志当环境记录。）
- 运行时安装 **3 个原生 hook**（`ACTIVE: 3 native hooks installed`）。

**功能实现细节（可作为仁王 1 的规格参考）**：

- 精防窗口：从"新按下防御"的输入边沿起算 250 ms，按住不刷新（`window_ms`）。
- 自身收益：回精（`None` / `Balanced=最大精力/6` / `Fixed`）、格挡耗精减免百分比、额外妖力（Anima）。
- 对敌效果：当前精力伤害、妖怪有效精力上限伤害、HP 伤害（可致死），作用于**本次被格挡攻击的来源**，无需锁定。
- 受击冲击：`None/Light/Heavy`，数值硬编码为 `light_reaction=18`、`heavy_reaction=4`、`null_event=1`。
- 妖怪上限耗尽补足：`cap_gate` 条件 `0x25C`，`scope=one_native_consume`，不强制指定动作号。
- **音效**：自解码 WAV，用 **XAudio2（COM 激活，`ole32` 的 `CoCreateInstance`）** 播放
  —— 所以 DLL 只导入 `ole32/bcrypt/USER32/KERNEL32` 四个 DLL，没有任何音频/图形 DLL 依赖。
  **这部分与游戏引擎无关，可原样移植到仁王 1。**
- **特效**：走**游戏自己的 effect factory**（`V.F.X. experiment factory_call=... factory=...`），
  在创建期改颜色参数。这部分**强依赖引擎**，仁王 1 需要另找锚点，或降级/砍掉。
- INI 热更新、Ctrl+Shift+F10 导出日志、UTF-8/UTF-16 支持、配置校验失败回退上一份有效配置。

### 2.4 仁王 1 `nioh.exe` 静态分析结果（本次实测）

| 项 | 值 |
| --- | --- |
| PE | x64，ImageBase `0x140000000`，8 个段 |
| `.text` | RVA `0x1000`，vsize `0x1199498`（≈18.4 MB），rawsize `0x1199600`，**熵 8.000** |
| `.rdata` | RVA `0x119B000`，6.0 MB，**熵 5.06，完整可读**，19621 条可读字符串 |
| `.bind` | RVA `0x303B000`，206 KB，**入口点 `0x303B310` 在这里**（Steam DRM 装载 stub） |
| 导入 | `DINPUT8.dll!DirectInput8Create`、`XINPUT1_3.dll`、`d3d11.dll!D3D11CreateDevice`、`steam_api64.dll`、`EOSSDK-Win64-Shipping.dll` |
| 音频数据 | `sound/**/*.ktsl2asbin`、`*.ktsl2stbin`、`*.g1l`（KT 自家 ktsl2 音频容器） |

**`.text` 加密的判定证据（三条独立指标一致）**：

1. 熵 = 8.000，且 256 个字节值**完全均匀**（每个约 72,700 次，18.4 MB / 256 ≈ 71,900）。
   正常 x64 代码有强烈的 `00`/`CC`/`48`/`8B` 偏置，绝不可能均匀。
2. `E8`（call rel32）目标落在 `.text` 段内的比例：**0.41%**。真实代码里这个比例是 ~95%+，随机数据≈0%。
3. 常见 MSVC 函数序言 `48 89 5C 24`、`48 8B C4` 在 `.text` 中出现 **0 次**；
   而同样的检测器在 `.bind` 段的入口 stub 上能正常命中这些序言和合法指令。

**已确认的引擎侧可利用符号（来自未加密的 `.rdata` / RTTI）**：

- 命名空间：`ktgl`（Koei Tecmo Graphics Library）、`ktsl2`、`scl`
- 角色状态架构：`Character::SetActionID`、`Character::GetActionID`、`Refer::PrevActionId`、
  `Character::IsNowState`、`Player::IsNowState`
- **防御相关**：`Refer::IsAttackGuard`、`AddStateObjectAbsoluteGuard@Character`、
  `AddStateObjectDefense@Character`、`AddStateObjectDefenseElement@Character`、
  `AddStateGuardPenetration@Character`、`AddStateObjectGuardianPowerless@Character`
- **精力相关**：`Player::RecoverStamina`、`Refer::Stamina`、`Refer::StaminaRate`、
  `AddStateObjectStaminaDamageRate@Character`、`AddStateObjectStaminaRecover@Character`、
  `AddStateObjectStaminaRecoverDown@Character`、`AddStateObjectUseStaminaRate@Character`、
  `AddStateObjectUseStaminaRateAttack/Dodge@Character`
- **输入**：`Input::Button`、`Input::StickToTarget`、`ActionInputButton@<anon>`
- HUD 按键提示：`GUARD_TRIANGLE`、`GUARD_SQUARE`、`GUARD_CROSS`、`GUARD_AND_TRIANGLE`
- 伤害链路：`Chara::IsDamagePlayer`、`Shot::IsParentCharaDamage`、`Script::StopDamage`

> 这些 `Xxx::Yyy` 是 KTGL 的**脚本/节点图名称表**。它们和函数指针、脚本字节码同处 `.rdata`/`.data`，
> 是可以离线做交叉引用推导的——即使代码段加密，这也是仁王 1 相对仁王 2 反而更"有据可依"的一点。

### 2.5 联网调研要点

- **仁王 1 没有 Denuvo**：["Nioh: Complete Edition will not be using the Denuvo anti-tamper tech"](https://www.reddit.com/r/Games/comments/787nsv/nioh_complete_edition_will_not_be_using_the/)。
  磁盘上的代码加密来自 **Steam DRM (SteamStub)**——它的特征正是"**.bind 段存放装载 stub + `.text` 加密**"，
  见 [A (Small) Peek Into SteamDRMP.dll](https://atom0s.com/posts/2015/2015-03-26-a-small-peek-into-steamdrmp-dll/)。
  **Steam DRM 不是反作弊**：不做完整性校验、不拦注入，只在启动时解密 `.text`。
  这意味着：**进程内存里是干净的、可 AOB 扫描的代码**，而磁盘上不是。
- **引擎**：仁王系列使用 Koei Tecmo 自研引擎（低层库 `ktgl`/KTGL，后称 Katana Engine），
  见 [Katana Engine - Wikipedia](https://en.wikipedia.org/wiki/Katana_Engine)。仁王 1/2/3 属同一技术血缘。
- **仁王 3 的「Guard Parry / 精准防御」官方行为**（来自 [nioh3.net 战斗指南](https://nioh3.net/guides/combat/)）：
  短按 L1 在命中瞬间触发；成功时**精力消耗为 0**、敌人硬直约 1 秒并造出反击窗口；
  对**所有敌人**生效（人类与妖怪）；**对投技和红光 Burst Attack 无效**；窗口比普通格挡紧、比闪避宽松。
- **仁王 1 已有"瞬間防禦/ジャストガード"概念**：逆波（Backwave）就是"原地短按 L1 的及时格挡"，
  是太刀技能且主要对人类生效；仁王 1 里还能拿"瞬防"强化格挡强度。
  → **这提示引擎内部很可能已存在一个"及时格挡"的状态位**。如果它存在，精防 MOD 可以直接挂它，
  而不是从零重建 250 ms 计时逻辑。**这是阶段 2 要优先验证的第一件事。**
- **反作弊/存档**：仁王 1 有联机存档校验，社区经验是改数值可能被标记存档
  （[FearlessRevolution 仁王 CE 表帖](https://fearlessrevolution.com/viewtopic.php?t=5355)）。
  DLL 注入本身（改代码不改存档）风险低，但仍建议**离线测试**。
- **仁王 1 的代码级 MOD 生态基本空白**：能找到的都是存档修改、CE 表、贴图/数据替换。
  Nexus 上的 DLL 插件加载器都是 [仁王2 mod 671](https://www.nexusmods.com/nioh2/mods/671) 和
  [仁王3 mod 49](https://www.nexusmods.com/nioh3/mods/49) / [kassent/NIOH3-Plugin-Loader](https://github.com/kassent/NIOH3-Plugin-Loader)，
  **没有仁王 1 的对应物**。也就是说：这个 MOD 做出来会是仁王 1 第一个真正意义上的代码级 MOD。

## 三、技术路线

```
[Steam 启动 nioh.exe]
        │  Steam DRM 解密 .text（内存中）
        ▼
[dinput8.dll 代理加载器]  ──►  [mods\Nioh1Probe\Nioh1Probe.dll]  ← 阶段 0：内存镜像导出探针
        │
        │  导出：模块基址 / 段表 / 解密后 .text / RTTI 与字符串带 RVA / vftable 清单
        ▼
[离线静态分析]  ──►  定位锚点  ──►  产出 AOB + ABI 校验规则
        │
        ▼
[mods\Nioh1PerfectGuard\Nioh1PerfectGuard.dll]  ← 阶段 3~5：真正的 MOD
```

**为什么要"两段式"**：锚点必须是**内存中运行态**的字节。所以先用一个一次性探针把镜像 dump 出来，
离线把锚点找齐、把校验规则写好，再让正式 MOD 在运行时做 AOB 扫描。
这和仁王 2 那个 DLL 的做法完全一致（它也是运行时扫描内存镜像，而不是扫磁盘文件）。

## 四、仁王 1 功能规格（相对仁王 2 的增删）

仁王 1 没有仁王 2 的妖力（Anima）、妖怪有效精力上限、妖怪化（Yokai Shift），
所以必须砍掉对应功能；同时仁王 1 的"灵"（Living Weapon）槽不建议做回复。

| 功能 | 仁王 2 版 | 仁王 1 版计划 | 说明 |
| --- | --- | --- | --- |
| 精防窗口 | 250 ms，新按下起算 | ✅ 保留 | 若引擎已有"及时格挡"状态位，优先复用 |
| 自身回精 | `None/Balanced(最大/6)/Fixed` | ✅ 保留 | 仁王 1 最大精力概念一致 |
| 格挡耗精减免 | 0–100% | ✅ 保留 | 仁王 1 的格挡耗精路径需重新定位 |
| 额外回妖（Anima） | 0–100 | ❌ 删除 | 仁王 1 无妖力 |
| 对敌当前精力伤害 | 200 | ✅ 保留 | |
| 对敌妖怪精力上限伤害 | 100 | ❌ 删除 | 仁王 1 无此概念 |
| 妖怪上限耗尽处决补足 | 有 | ❌ 删除 | 依赖仁王 2 的 cap 机制 |
| 对敌 HP 伤害 | 50，可致死 | ✅ 保留 | |
| 轻重受击冲击 | `None/Light/Heavy` | ⚠️ 待定 | 反应 ID（18/4/1）是仁王 2 的，仁王 1 需重新标定 |
| 精防后提前接续操作 | 开/关 | ✅ 保留 | 需定位后摇取消路径 |
| 自定义音效 | WAV + 音量 | ✅ 保留（可原样移植） | XAudio2 与引擎无关 |
| 视觉特效 | 完整/简洁/关 + 颜色 | ⚠️ 降级为可选 | 依赖引擎 FX factory 锚点，找不到就砍 |
| INI 热更新 + 中英双语 | 有 | ✅ 保留 | 照搬架构 |
| Ctrl+Shift+F10 导出日志 | 有 | ✅ 保留 | 排障必需 |

**设计原则**：不改原生判定、不强制触发逆波/胧、不把不可防御攻击变成可防御
（与仁王 2 版一致，也避免破坏游戏平衡和联机数据）。

## 五、分阶段实施计划

> 每个阶段都有**明确的验收标准**和**失败退出点**。阶段 2 是唯一的高不确定环节，
> 如果阶段 2 失败，会带着证据回来重新决策，而不是硬做下去。

### 阶段 0 · 环境与探针（预计 0.5 天）

**做什么**
1. 把 `dinput8.dll` 加载器放入仁王 1 游戏目录，建 `mods\` 目录。
2. 编写最小探针 `Nioh1Probe.dll`（约 200 行 C++）：
   - 加载后写 `loader.log` 同级日志，报告 `GetModuleHandleW(NULL)` 基址、PE 段表；
   - 把解密后的 `.text`（以及可选的全部段）dump 到工作区；
   - 输出 RTTI 描述符 + 字符串 + RVA 清单；扫描 `.text` 里的 vftable 指针群。
3. 准备离线分析链：Python + capstone（本机已有）、Ghidra 或 IDA Free、x64dbg（备用）。

**交付物**：`Nioh1Probe.dll`、`nioh1.dump.text.bin`、`nioh1.dump.meta.json`、`loader.log`
**验收标准**：dump 出来的 `.text` 熵 **< 6.5**、`E8` 段内命中率 **> 90%**、能反汇编出合法函数。
**注意**：探针只读内存、只写工作区文件，不修改游戏任何文件。

### 阶段 1 · 镜像重建与符号化（1–2 天）

**做什么**
1. 用 dump 重建可被反汇编器加载的镜像（修 PE 头、段对齐、恢复导入表、生成 `.idb`/`.gpr`）。
2. 把 `.rdata` 的字符串与 RTTI 按 RVA 批量注释到反汇编器里，自动生成 `class → vftable → 函数` 映射。
3. 用 `AddStateObject*` / `Refer::*` / `Player::*` 这些节点名做交叉引用，定位角色状态机核心。

**交付物**：可分析的镜像 + 符号注释脚本 + 「关键类/函数候选清单」
**验收标准**：能在反汇编器里按名字跳到 `Character::GetActionID`、`Refer::IsAttackGuard` 等函数体。

### 阶段 2 · 锚点定位（3–7 天，**最大不确定性**）

按优先级逐个攻：

| 编号 | 锚点 | 用途 | 难度 |
| --- | --- | --- | --- |
| A0 | **引擎原生"及时格挡"状态位** | 若存在，直接当精防判定源 | 低（若存在） |
| A | 玩家防御输入边沿 + 防御状态 | 窗口起算点 | 中 |
| B | 玩家精力结算（格挡耗精） | 减免 / 回精 | 中 |
| C | 成功格挡事件 + 攻击来源 | 触发精防、指定对敌目标 | **高** |
| D | 敌人精力 / HP 结算 | 对敌削精、HP 伤害 | 中高 |
| E | 后摇取消路径 | `CancelRecovery` | 中 |
| F | 受击反应触发（轻/重冲击） | 冲击档位，需重新标定 ID | 中 |
| G | effect factory | 视觉特效（**可选**） | 中高 |
| — | 音效（XAudio2） | 无需锚点 | 无 |

**每个锚点的交付要求**（沿用仁王 2 版的严格度）：唯一 AOB 字节串 + 掩码、匹配数必须为 1、
CALL 目标 ABI 校验、写入目标权限校验、失败时不安装（不半死）。
**验收标准**：每个锚点在**两次独立启动**中都稳定命中同一 RVA，且 ABI 校验通过。

**如果 C（成功格挡事件/攻击来源）找不到**：降级方案是用 A（输入边沿）+ 防御状态近似判定，
精度下降（无法精确知道"这一下是否被格挡"），对敌效果的"攻击来源"改为锁定目标或最近敌人。
这个降级会写进 README 明确告知。

### 阶段 3 · 检测原型（2–3 天）

**做什么**：`Nioh1PerfectGuard.dll` 只做**检测 + 日志**，不做任何收益。
F10 导出「按下防御时间 / 格挡成功时间 / 间隔 / 是否落在窗口内」。
**验收标准**：日志判定与游戏内实际"及时格挡"表现一致（用逆波场景交叉验证）。

### 阶段 4 · 收益实现（3–5 天）

按 A → B → D → E → F 的顺序逐项接入并逐项游戏内验证：
回精 → 格挡耗精减免 → 对敌精力伤害 → 对敌 HP → 提前接续 → 轻重冲击。
**验收标准**：每项独立验证通过；关掉 MOD 后游戏行为与原生完全一致（可回退）。

### 阶段 5 · 收尾与打包（1–2 天）

INI（中英双语，照仁王 2 版分区结构，删掉不适用的键）、音效、特效（若 G 成功）、
日志快捷键、`SHA256SUMS.txt`、`README_CN.md` / `README_EN.md`、回退说明。
**验收标准**：全新环境按 README 手动复制即可安装；卸载只删本 MOD 目录。

**总工期估计：约 10–20 个工作日**（取决于阶段 2 的顺利程度）。

## 六、风险清单

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 阶段 2 锚点找不到（尤其「成功格挡事件」） | 高 | 已定义降级方案；先做 A0 验证引擎是否已有及时格挡状态 |

## 七、需要你确认的事项

1. **是否同意为定位锚点反复启动游戏？**
   阶段 0–2 需要你配合启动游戏多次（估计 5–20 次），每次我用探针 dump 一段内存。
   这是**唯一**能拿到解密代码的途径。
2. **是否允许在仁王 1 游戏目录放置文件？**
   `dinput8.dll`（加载器）+ `mods\` 目录。全部可一键删除回退。若你希望，我也可以只做只读分析、
   把安装步骤写成文档交给你自己执行。
3. **DRM 处理方式（二选一）**
   - **方案甲（推荐，默认）**：只用运行时内存 dump，**完全不碰 DRM**。
   - **方案乙（加速）**：额外用 Steamless 对 `nioh.exe` 的**副本**做离线解包，方便用 IDA/Ghidra 静态分析。
     这属于绕过 DRM 的技术手段，**需要你明确同意**；不做也不影响最终结果，只是慢一些。
4. **功能范围**：先做阶段 3 的「纯检测原型」验证可行性后再继续，还是直接一次做到阶段 5 全功能？
5. **视觉特效（G）**要不要保留？如果保留会增加 2–4 天且成功率一般；砍掉则只有音效反馈。
6. **是否接受"离线测试"的建议**？（联机存档标记风险）
